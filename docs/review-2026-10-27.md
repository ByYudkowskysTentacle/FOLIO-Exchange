# Design and function review, 27 October 2026

Eight independent reviewers each read the codebase through one lens: architecture, the export pipeline, large catalogues, security and privacy, the command line and setup, the local page, spec coverage, and tests. A second reviewer checked every finding against the code. Of 74 findings, 71 held up (some with a better fix, noted below) and 3 were refuted. A planned second round on four thinly covered areas (field value fidelity, unattended scheduled operation, living with upgrades over time, feed overlay as a policy boundary) did not run because of usage limits.

## Fix now

All five were fixed on 27 October 2026 (branch `claude/fix-now`), each with regression tests in `tests/test_fix_now.py` and `tests/test_ui.py`.

1. **Make setup safe to re-run** (OPS-2, TEST-1, ARCH-3, OPS-3, OPS-7, OPS-8, TEST-4; up to high). init stores a refused password and offers it again (account lockout risk); it wipes a feed or site file that has a YAML error, re-enables a paused feed, drops comments, bypasses config.py's ${ENV} and overrides, and crashes on the alert step without a keyring.

A stalled SFTP transfer has no timeout and holds the lock for days; a failed staged upload leaves .part files at the vendor; the advice after a failed delivery can send an older run; two feeds can overwrite each other's files at one destination; an unconfirmed host key is used at once.

A full sync fails if records are added during it; missing MARC (ECS shared records) silently becomes brief records; clock skew can lose updates; one bad SRS record fails the feed; items under suppressed holdings are exported; a corrupt cache fails forever.
5. **Page bugs** (UI-3, UI-1, UI-2, UI-4, UI-5; up to medium). Ctrl+Enter behind the Send dialog starts a Run and drops the send; the whole view is rebuilt every 700 ms; results can show under the wrong feed; a reload loses a running job; Ctrl+C kills a release mid-flight.

### Make setup safe to re-run

**OPS-2. Init keeps a refused FOLIO password and defaults to reusing it** (high severity, effort S, verified: confirmed)

- Files: `src/folio_exchange/wizard.py:229-248`, `docs/dry-run.md:129`
- Problem: A librarian who mistypes the password gets a message that says nothing was saved, while the bad password is now in Credential Manager. Each later `init` where they press Enter sends the same wrong password again. The fix in the troubleshooting table (`secret set folio`) fails with "No site.yaml", because site.yaml is only written after a successful login. Eureka's Keycloak and Okapi's mod-login both lock an account after a few failures, so the guide's promise that FOLIO-Exchange "cannot lock the account" does not hold during setup.
- Change: Keep the typed password in memory and call `credentials.store` only after `client.login()` succeeds. If a stored password is refused, delete it, or at least make the next "Keep it?" default to no and say "The stored password was refused last time." Change "Nothing was saved" to say exactly what was and was not kept. In docs/dry-run.md:129, say that during setup you re-run `init` and answer n to "Keep it?". Add a wizard regression test for a refused password followed by a re-run.

**OPS-1. Transient login errors crash check and init with a traceback** (medium severity, effort S, verified: confirmed)

### Deliveries that cannot hang or mislead

**PIPE-3. Stalled SFTP transfer hangs the run with no timeout and no alert** (medium severity, effort S, verified: confirmed)

- Files: `src/folio_exchange/delivery.py:76-86`, `src/folio_exchange/delivery.py:124-166`, `src/folio_exchange/schedule.py:188`, `src/folio_exchange/cli.py:323-328`
- Problem: One stalled upload holds the site lock and the scheduled task for up to three days. Task Scheduler doesn't start new instances while it runs, so no `run --due` runs and no overdue warning or alert fires. Every feed stops silently until Windows kills the task and the next run's fail_stale finally sends an alert.
- Change: After connecting, call `client.get_transport().set_keepalive(30)`. On the SFTP channel, call `sftp.get_channel().settimeout(300)` (or a `delivery.timeout_seconds` setting) so a stalled transfer raises and becomes a normal failed or partial delivery. Optionally, have `run --due` alert when the lock-holder PID in the lock file has held it longer than a few hours. Test with a fake channel whose write blocks.

**TEST-3. Failed staged SFTP upload leaves .part files at the vendor; pin check never exercised** (medium severity, effort M, verified: partly)

- Files: `src/folio_exchange/delivery.py:252-260`, `src/folio_exchange/delivery.py:262-272`, `src/folio_exchange/delivery.py:322-329`, `src/folio_exchange/delivery.py:163-171`, `src/folio_exchange/delivery.py:295-301`, `tests/test_units.py:92-103`
- Problem: File names carry `{date}`, so every interrupted delivery leaves a new orphan `*.part` (sometimes truncated) on the vendor's server. Vendor pickup jobs that glob the folder may ingest them, while the operator is told nothing changed there. A regression in the pin comparison (for example, switching to AutoAddPolicy, or comparing case-insensitively) would pass CI.
- Change: In the staged branch, wrap phase 1 in try/except. On failure, try sftp.remove for every staged and in-flight .part file and swallow any errors. Record which .part names could not be confirmed removed, and have deliver() report them ('Nothing was renamed into place; these temporary files may remain at the vendor: ...'). Do not say 'Nothing was changed there'. Add unit tests: (a) a put failure with a working session removes the .part files; (b) a put failure where remove also raises names the leftovers in the message; (c) take the policy from set_missing_host_key_policy.call_args, then check that a matching fingerprint is accepted and a different one raises SSHException; (d) posix_rename raising OSError falls back to remove, then rename. The in-process paramiko SFTP server is a nice-to-have, not needed for this fix.

### Sync that tolerates a busy tenant

**PIPE-2. Full sync fails when records are created during it** (medium severity, effort S, verified: confirmed)

- Files: `src/folio_exchange/sync.py:143-153`, `src/folio_exchange/sync.py:163-174`, `src/folio_exchange/client.py:229-241`
- Problem: A full sync (every 30 days, and after any deletion, which is most weeks in an active library) that overlaps a batch load of more than 0.1% of the table fails the whole run. The message tells the operator to lower page_size, which is wrong and doesn't help, and the cache stays 'incomplete' until a full sync happens in a quiet window. Scheduled deliveries are missed in the meantime.
- Change: Count before paging as well (`before = count(path)`) and check `n` against `min(before, after)`, or against `count('metadata.createdDate<"<started>"')`, so creations during the sync don't count as a shortfall. Keep the existing message only for a real shortfall, and say 'records were added in FOLIO during the download' when `after > before`. Add a mock test that inserts records behind the cursor mid-sync.

**PIPE-6. Missing MARC (e.g. ECS shared records) silently becomes brief records** (medium severity, effort M, verified: partly)

- Files: `src/folio_exchange/sync.py:100-105`, `src/folio_exchange/sync.py:235-250`, `src/folio_exchange/config.py:37`, `src/folio_exchange/build.py:156-163`, `src/folio_exchange/checks.py:1-40`
- Problem: On an ECS member tenant (or a tenant whose SRS load was incomplete), the vendor gets brief 245/100/020 records instead of full cataloguing for most of the collection. Every run reports success. The operator would only notice when collectionHQ's matching degrades. The missing set is also re-requested on every run.
- Change: Add a warning, not a block, when MARC-source instances end up without MARC above a small threshold: give the count and a few HRIDs in the run report and alert. When any CONSORTIUM-MARC instance is seen with srs_include_shared false, say 'this looks like an ECS member tenant; set folio.srs_include_shared: true' in the run report and in `check`. Optionally cap the missing-MARC retry (for example once a day, using one meta timestamp rather than per-instance records).

**PIPE-8. Delta watermark uses the PC clock; skew over 10 min loses updates** (low severity, effort S, verified: confirmed)

- Files: `src/folio_exchange/sync.py:85`, `src/folio_exchange/sync.py:126`, `src/folio_exchange/sync.py:158`, `src/folio_exchange/sync.py:28`
- Problem: Library PCs outside a domain, or with a dead CMOS battery, often drift. Any skew beyond 10 minutes silently drops some updates (status changes, new barcodes, location moves) from every delta, for up to a month. Nothing in the report shows it.
- Change: Take the watermark from FOLIO's clock: use the HTTP `Date` header of the first page response (or the max metadata.updatedDate seen in the sync, if larger) rather than `now_utc()`. Log a warning when the PC and the server differ by more than a few minutes, which `check` can also report. Keep the 10-minute overlap for in-flight transactions.

**PIPE-4. One malformed SRS record fails the whole feed, unnamed** (low severity, effort S, verified: partly)

- Files: `src/folio_exchange/marc.py:19-22`, `src/folio_exchange/marc.py:55-60`, `src/folio_exchange/marc.py:172-195`, `src/folio_exchange/build.py:155-167`, `src/folio_exchange/marc.py:63-64`
- Problem: A single odd record among hundreds of thousands stops every delivery for the feed, scheduled run after scheduled run. The error doesn't name the instance, so a librarian can't find and fix it. Parse failures are hidden inside the 'generated' count. Stray separator characters from migrated data corrupt the file for any vendor parser that splits on terminators.
