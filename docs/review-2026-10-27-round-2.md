## Data sent to collectionHQ

**FIELD-legacy-note-parsing. Legacy note values are parsed leniently and silently: wrong or missing Created_date, Last_circ_date and Number of loans, with nothing in the report** (medium severity, verified: confirmed)

- Files: `src/folio_exchange/dates.py:20-24 (dateutil fallback)`, `src/folio_exchange/fields.py:132-136 (_int)`, `src/folio_exchange/fields.py:159-163 and 194 (legacy values used)`, `src/folio_exchange/build.py:250; identical code in FOLIOHQ src/folio_chq/dates.py:13-27 and fields.py:109-113, so byte parity cannot catch it`
- Problem: The legacy settings exist to replace FOLIO's migration-day created date and to carry old loan history. The note values go through dateutil's free-text parser and a bare int(float()) with no format, no plausibility bounds and no counter. Four things go wrong. (1) Two-digit years pivot forward: in 2026, '06-12-68' becomes 2068-06-12. (2) Partial dates are filled in from today's date: '1998' becomes 1998-10-27 and 'March 1998' becomes 1998-03-27, so the value changes on every run. (3) A future legacy last-checkout date (from that pivot or a typo such as 2205) wins latest() against every real FOLIO checkout, for good. (4) A note with any label text ('Created: 1998-03-15', '1998-03-15 (Sierra)', 'Checkouts: 12', '12 (since 2003)') parses to nothing: the item silently falls back to the migration date, or the count becomes 0. Neither BuildReport nor the run report counts legacy notes that were present but unusable, so a library whose migration wrote labelled notes gets migration-day created dates and FOLIO-only loan counts for its whole migrated collection, run after run, while every run reports success.
- Scenario: Feed with legacy: {created_date_note_type, circ_count_note_type, last_circ_date_note_type} and options.timezone America/Detroit. Item notes give: created '06-12-68' -> Created_date '2068-06-12 00:00:00'; created '1998' -> '1998-10-27 00:00:00' today and '1998-10-28' tomorrow; last checkout '11-03-72' with a FOLIO checkout on 2026-09-01 -> Last_circ_date '2072-11-03 00:00:00'; count 'Checkouts: 12' with 3 FOLIO loans -> Number of loans 3; created 'Created: 1998-03-15' -> Created_date is the FOLIO migration timestamp. collectionHQ then reads old stock as new or recently used, and undercounts its use, which skews weeding and dead-stock analysis.
- Change: Parse legacy notes strictly in RowBuilder rather than through the general parse(). For dates, accept ISO 8601 plus an optional legacy.date_format (strftime pattern) in the feed. Require day, month and year: with dateutil, pass a sentinel default and reject the result if any part came from it. Map two-digit years to the past (never later than this year), and reject dates before about 1800 or after today plus one day. For counts, accept a plain non-negative integer (thousands separators allowed), optionally after a label with a single number such as 'Checkouts: 12'. Count notes that are present but rejected, per note type, in BuildReport (legacy_unparsed, with a few item HRIDs), and show them as a run-report warning and in preview. Make the same change in FOLIOHQ's legacy tool, or note the difference, so the parity test still holds. Add regression tests for the cases above.
- Verifier: Read src/folio_exchange/dates.py:13-27 (fromisoformat, then dateutil.parse with no default, no dayfirst, no bounds) and fields.py _int (int(float(text))) and RowBuilder.build lines 60-64/95 (legacy values used directly; latest() is a plain string max). Ran a script in the scratchpad (scratchpad/vf/r.py) with the repo venv, tz America/Detroit: norm('06-12-68') -> 2068-06-12T04:00:00; norm('11-03-72') -> 2072-11-03; norm('2205-03-15') -> 2205-03-15; norm('1998') -> 1998-10-27 (today's month and day); norm('March 1998') -> 1998-03-27; norm('Created: 1998-03-15') and norm('1998-03-15 (Sierra)') -> None; _int('Checkouts: 12') = 0, _int('12 checkouts') = 0, _int('1 234') = 0, _int('1.234') = 1. Because latest() compares strings, a 2068/2072 legacy last-checkout outranks every real FOLIO checkout permanently. build.py:250 and BuildReport have no counter for present-but-unusable legacy notes, and the only tests (test_units.py:26, test_end_to_end.py:88-89) cover clean values. FOLIOHQ's layout.md and setup.md give no required format for these notes, so free-text values are what the code is meant to accept. Mitigations that narrow it but do not remove it: the first delivery is held for a person, and preview shows the values; but later runs are unattended and the outcome only depends on how the library's migration wrote its notes. The two-digit-year pivot and the silent 0 or None for labelled values are the strongest parts; the 'partial date from today' case needs year-only notes, which are less common.
- Fix note: The proposed fix is sound. Also: dateutil reads 'NN/NN/YYYY' month-first, so a UK or Australian library's '03/04/1998' becomes 4 March, not 3 April; the optional legacy.date_format (or a dayfirst setting) covers that too. Keep FOLIOHQ's legacy tool in step or record the difference, as the parity test compares outputs.

Only the item-ratio check stands in the way, and it passes when the other tenant is a refreshed copy of production, which is the usual set-up for a FOLIO test environment. Nothing is alerted with `alerts.on: failure`, because the run succeeds.

In `hold_reason`, hold when it differs from the last delivery to that destination ('first delivery from FOLIO X; the last came from Y'), and treat a delivery that recorded no source as matching, as is done for layouts. - Verifier: Read runner.hold_reason (runner.py:95-110): it holds only on no previous delivery to the destination, a recipe major change or a layout_note. folio_source/other_folio (runner.py:425-452) only moves the cache aside and forces a full sync. The run report (runner.py:269-274) has no FOLIO source field. config.py:244 applies FOLIO_URL/FOLIO_TENANT over site.yaml, and setupops.connect rewrites base_url and tenant on an existing site.yaml. Reproduced in a scratch pytest using the repo fixtures: run chq (held), release, then a second MockFolio with titles prefixed 'TEST TENANT COPY' set as FOLIO_URL, then `run chq`. Result: exit 0, status success, delivered True, held None. data/ held cache.other-folio-<stamp>.sqlite, and the vendor-drop files contained 'TEST TENANT'. Severity lowered from high: it needs an operator to point a delivering site at another tenant (itself a mistake), and the item-ratio check still blocks a smaller tenant. When the test tenant is a fresh copy of production, the data sent is close to production's, so the harm is limited to the difference.
- Fix note: The suggested fix is sound. Store the normalised folio_source() string in the report and runs row, and hold when it differs from the last delivery to the same destination. **FIELD-legacy-date-overflow-crash. A legacy date of 0001-01-01 (or 9999-12-31 late in the day) crashes every build with OverflowError in zones on the wrong side of UTC** (low severity, verified: confirmed)

- Files: `src/folio_exchange/dates.py:25-27 (astimezone outside the try)`, `src/folio_exchange/dates.py:44-45 (fmt)`, `src/folio_exchange/fields.py:160-161`, `src/folio_exchange/build.py:250 (no per-item guard)`
- Problem: parse() catches ValueError and OverflowError only while parsing the text. The conversion afterwards, dt.replace(tzinfo=naive_tz).astimezone(timezone.utc), is unguarded. A legacy note holding the common null-date placeholder 0001-01-01, read in a feed time zone east of UTC (any of Europe, Africa, Asia or Australia), converts to a UTC time in year 0, and Python raises OverflowError. The same happens for 9999-12-31 with a time late in the day in a zone west of UTC. RowBuilder.build is called per item with no try, so a single such note aborts the whole build. Every scheduled run then fails with 'date value out of range', which names no item, note type or setting, and the operator cannot tell which record to fix.
- Scenario: Feed with legacy.created_date_note_type and options.timezone Australia/Sydney (or Europe/Berlin). One migrated item has the created-date note '0001-01-01' or '01/01/0001'. Every run of the feed fails at build and nothing is delivered until someone finds the item by hand.
- Change: In dates.parse, wrap the replace(...).astimezone(...) step (and the astimezone in fmt) and return None on OverflowError or ValueError. The plausibility bounds from FIELD-legacy-note-parsing would also reject these placeholders, and they should be counted as unusable legacy values, not crash the run. Add a regression test with '0001-01-01' and an eastern time zone.
- Verifier: dates.parse guards only the parse step; dt.replace(tzinfo=naive_tz).astimezone(timezone.utc) at lines 25-27 is unguarded. Reproduced: norm('0001-01-01', ZoneInfo('Australia/Sydney')) and Europe/Berlin, and '01/01/0001', raise OverflowError: date value out of range; America/Detroit and America/Los_Angeles raise it for '9999-12-31 23:00:00'; UTC and western zones accept 0001-01-01. RowBuilder.build is called at build.py:250 with no per-item guard, so one such note fails the whole build; runner.py:347 catches it at the top level and records 'OverflowError: date value out of range' with no item, note type or setting named. The run is reported failed (not silent) and alerts fire, but the operator has nothing to locate the record by, and every scheduled run fails until the note is found. Severity low because the trigger is narrow: a year-1 placeholder or a 9999-12-31 value with a late time, in a legacy note type the feed names, in a zone on the wrong side of UTC.
- Fix note: Catching OverflowError and ValueError around the conversion in parse() and fmt() is right; better still, return None and count it as an unusable legacy value (per the first finding) so the run report names the item HRID instead of failing the feed.

This lasts until someone answers the prompt or closes the window.
- Scenario: An operator follows the guide, runs `folio-exchange release chq`, reads the summary and leaves the console open at 'Send these files now? [y/N]' over a weekend. Every feed on the site misses its scheduled slots. The heartbeat monitor stays green and the page says a run is in progress.

- Verifier: Read runner.release (src/folio_exchange/runner.py ~612-645): it takes RunLock and History, then calls confirm(summary) inside the with-block; cli.cmd_release's confirm calls _yes(input). cmd_run --due catches LockBusy, logs INFO 'Skipping this hour' and returns 0, and the heartbeat goes in the start/finally of cmd_run. record_due_start runs every pass, so in feedops.task_status 'since - last' is negative and the state stays 'running' with the 'first sync can take several hours' text. It is a silent delay of every feed on the site, with intermediate daily slots folded into one run, not lost data. **CACHE-diskfull-treated-as-corruption. A full disk (or any SQLite OperationalError) is treated as a damaged cache: the healthy cache is moved aside and can be overwritten within the same second** (medium severity, verified: confirmed)

- Files: `src/folio_exchange/runner.py:436-467 (sync: except sqlite3.DatabaseError -> quarantine, then retry with full=True); src/folio_exchange/runner.py:297-301 (the same in run_feed around build, which can spill temp B-trees to %TEMP%); src/folio_exchange/runner.py:413-422 (quarantine name is stamped to the second; Path.replace overwrites); src/folio_exchange/cache.py:49-56`
- Problem: sqlite3.OperationalError is a subclass of DatabaseError. So SQLITE_FULL ('database or disk is full'), SQLITE_IOERR, SQLITE_BUSY and SQLITE_CANTOPEN all take the corruption path built for PIPE-7: the cache is renamed to cache.broken-<stamp>.sqlite and a full download is started. With the disk still full, the second attempt fails at once: creating the new cache fails in Cache.__init__. Its quarantine then uses the same one-second stamp, and Path.replace overwrites the first quarantine, so the good cache is deleted, not set aside. The run reports 'The local cache is damaged … could not be rebuilt', which is not true. The next run is a full download of the whole catalogue. A full system drive (%TEMP%) during a large build also quarantines the cache through run_feed.
- Scenario: The data drive briefly fills (Windows Update, a backup, PERF-7's disk use) during an hourly sync. The healthy multi-GB cache is destroyed and replaced by an empty one. The alert says the cache was damaged. The next pass spends hours re-downloading every record and its MARC from FOLIO. If the second quarantine lands in a later second, both broken copies stay on the full disk and each hour adds another.
- Change: Quarantine only on real corruption: sqlite3.DatabaseError whose sqlite_errorcode is SQLITE_CORRUPT or SQLITE_NOTADB (Python 3.11+ exposes sqlite_errorcode; on 3.10 check the exception type and message, or run PRAGMA quick_check). Treat OperationalError (full, I/O, busy, can't open) as an ordinary failed run that names the disk or lock problem. Give quarantine names a unique suffix (as _new_run_dir does) so a later quarantine can never overwrite an earlier one. Add a regression test that makes Cache() and a write raise SQLITE_FULL.
- Verifier: In runner.sync (and run_feed around build), any sqlite3.DatabaseError, including OperationalError, quarantines the cache and retries with full=True. Cache.__init__ re-raises DatabaseError the same way. quarantine_cache stamps names to the second and uses Path.replace, which overwrites on Windows. I re-ran test_r2_diskfull.py: with upsert_items raising OperationalError('database or disk is full'), both attempts quarantine within the same second, only one cache.broken-<stamp>.sqlite remains (the original 65 KB good cache was overwritten by the second, partly rebuilt copy), and the error says 'The local cache is damaged … could not be rebuilt'. With space back, the next sync is 'full' for instances, holdings, items and loans. On a really full disk the second attempt fails at once in Cache() (PRAGMA journal_mode/executescript need to write), so the same-second overwrite is the likely outcome. If it falls in a later second, both copies stay on the full disk. Either way a healthy cache is thrown away and the next run downloads the whole catalogue. This is not in the first review: PIPE-7 asked for this quarantine and did not cover OperationalError.
- Fix note: Treat sqlite3.OperationalError (other than 'file is not a database' or 'malformed', which are DatabaseError/SQLITE_NOTADB or SQLITE_CORRUPT) as an ordinary failure. Python 3.10 lacks sqlite_errorcode, so for an ambiguous error run PRAGMA quick_check before quarantining. Use a unique quarantine name, for example adding the pid or a counter, as _new_run_dir does.

- Verifier: I re-ran test_history_write_failure_sends_no_alert_but_heartbeats: record_due_start fails and is only logged, then History.start_run raises OperationalError, which escapes run_many and main ('escaped main: OperationalError database or disk is full'). Keep the heartbeat semantics as documented, or optionally use the monitor's /fail URL. A small free-space check in check/site_warnings would also stop the stale-task text from misleading.

**SCHED-outage-exhausts-slot-alerts-lost. An outage of about three hours across a slot uses up every attempt; when the PC's network is down, no alert ever arrives and the slot is skipped** (low severity, verified: partly)

- Files: `src/folio_exchange/schedule.py:150-169 (attempts counted per slot, len(scheduled) < max_attempts); src/folio_exchange/config.py:42 (max_attempts_per_slot 3); src/folio_exchange/schedule.py:20,67-69 (weekly default = Sunday 02:00); src/folio_exchange/web/app.js:22 (page default 'Sun 03:30'); src/folio_exchange/notify.py:159-172 (a failed alert is only logged, never queued); src/folio_exchange/cli.py:368-371 and runner.py:550-567 (overdue is only logged, never alerted, and for a weekly feed fires only after the next slot also fails)`
- Problem: Scheduled attempts run hourly, so the default three attempts are spent within about three hours of the slot. After that the feed is not due until the next slot. When the outage is the PC's own network, all three failure alerts fail too ('Alert webhook failed: ConnectionError'), are only logged and are never sent again. Nothing later raises the missed slot: the overdue check is not an alert, and for a weekly feed it only fires after the following week's slot also fails. Even when the network is up and only FOLIO is down (for example a hosted upgrade), the week's delivery is dropped after three hours and needs a person.
- Scenario: A weekly feed on the page's default 'Sun 03:30'. Campus network maintenance runs Sunday 03:00 to 07:00. Attempts at 04:07, 05:07 and 06:07 fail with FOLIO unreachable, and each alert fails to send. At 07:07 the network is back and nothing is due. collectionHQ gets no file that week and nobody is told. The first sign is a 'recovered' alert or an overdue warning a week later.
- Change: Do not count an attempt that failed before reaching FOLIO (FolioUnreachable, or 5xx after the client's retries) against max_attempts_per_slot. Alternatively, back the retries off over the slot's interval (for example up to 24 hours for weekly feeds) rather than three consecutive hours. Store alerts that failed to send in history meta and send them on the next pass, with a note of when they were first raised. Alert, once, when a slot is given up after its last attempt.
- Verifier: I re-ran test_network_outage_spanning_the_slot_abandons_it_and_no_alert_ever_arrives: exit codes [1,1,1,0], 11 failed post attempts, three schedule/failed rows, and the fourth pass with the network back runs nothing and sends nothing. The code matches: schedule.is_due stops once len(scheduled) >= max_attempts, notify only logs a failed webhook, and runner.overdue for a weekly feed compares against the previous slot, so a missed week is not 'overdue' until the next slot also fails. Narrowing: stopping after three hourly attempts is the documented design (design.md:65 and :257). When only FOLIO is down and the PC's network works, the three failure alerts do arrive, so that half is not a silent defect. The silent case needs the PC's own alert path to be down through every attempt. After that, nothing re-raises the abandoned slot except the failed rows in history/feeds and the page, and the heartbeat monitor may not fire because dry-run.md tells operators to set a grace time of several hours. For collectionHQ's weekly full snapshot the next week's file catches up, so the vendor gets data a week late, not wrong data.

## A vendor key change, a moved folder

**SFTP-pin-breaks-on-new-key-type. A pinned SFTP fingerprint stops every delivery when the vendor adds a newer host key type next to the pinned one** (medium severity, verified: confirmed)

- Files: `src/folio_exchange/delivery.py:57-82 (_connect: fingerprint pin with no key-type preference)`, `src/folio_exchange/delivery.py:33-45 (host_key_fingerprints keeps only the SHA-256 value)`, `src/folio_exchange/setupops.py:522-546 (save_delivery stores only host_key_fingerprint)`
- Problem: The pin is one SHA-256 value with no key type, and `_connect` lets paramiko negotiate host keys in its default order (ssh-ed25519, ecdsa, rsa-sha2-*). An OpenSSH server often gains a new host key type in an OS or server upgrade while keeping its old key. When that happens, paramiko asks for the new type, the fingerprint no longer matches, and the run fails with 'This may not be the vendor's server … ask the vendor before going on', though the pinned key is unchanged and still offered. OpenSSH, and paramiko itself with known_hosts, ask for the known key type first, so they keep working. FOLIOHQ's setup.md records collectionHQ's pinned key as RSA. If collectionHQ adds an Ed25519 or ECDSA key, every library's scheduled deliveries fail with a 'wrong server' message. The vendor will say their key has not changed, and the page then refuses the RSA fingerprint they confirm ('ask them for the matching one').
- Scenario: A library pins collectionHQ's RSA key (SHA256:qt5H…), as setup.md shows. collectionHQ's server gains an ssh-ed25519 host key. The next weekly run fails with a host key mismatch; scheduled retries fail too. Each run alerts as a possible impostor server, and deliveries stop until someone gets and pins the Ed25519 fingerprint from the vendor.
- Change: Store the pinned key's type with the fingerprint (`host_key_type`, already available as `keys['type']` in save_delivery and the wizard). In `_connect`, put that type first in the transport's preferred host-key list (SSHClient.connect's `disabled_algorithms={'keys': [...]}`, or a Transport whose security options set key_types), as paramiko does for known_hosts. For pins without a stored type, retry the handshake once per key type and accept only a key whose SHA-256 equals the pin. The pin stays strict: only the pinned key is ever accepted.
- Verifier: _connect (delivery.py:57-82) uses SSHClient with a MissingHostKeyPolicy that compares one SHA-256 value, and sets no host-key algorithm preference. Paramiko 5.1.0 negotiates its default order (ed25519 before rsa). Reproduced with an in-process paramiko server: an RSA-only server gave ssh-rsa SHA256:FGLIO..., which was pinned. The same RSA key plus a new Ed25519 key made host_key_fingerprints report ssh-ed25519, and delivery._connect raised 'Host key for [127.0.0.1]:port is SHA256:Twd1..., expected SHA256:FGLIO...', though the pinned RSA key was still offered. FOLIOHQ's docs/setup.md line 60 records collectionHQ's key as RSA (SHA256:qt5H...), so every library would stop delivering if collectionHQ adds an Ed25519 or ECDSA key. The failure is loud (failed runs, alerts) rather than silent, and the way forward is to get and pin the new key's fingerprint, hence medium.
- Fix note: Store host_key_type next to the fingerprint and restrict negotiation to it, e.g. client.connect(..., disabled_algorithms={'keys': [every other type]}). Note that an ssh-rsa pin must allow rsa-sha2-512/256 as well. For old pins with no type, retry once per type the server offers and accept only the pinned SHA-256.

**SECRET-private-key-text-in-history. Key text pasted into delivery.private_key is accepted and copied into the audit log and the page's Activity view** (low severity, verified: confirmed)
