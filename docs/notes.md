# Working notes

_The project's running record: where things stand, the decisions so far and why, and what's been learned about FOLIO and collectionHQ. Last updated 13 November 2026. Goals and scope are in [spec.md](spec.md), how v1 is built is in [design.md](design.md), and terms are explained in the [docs index](README.md#terms)._

## Where things stand

- **FOLIO-Exchange** v1 is built and tested offline, and has run against FOLIO's public Eureka test system (see below). Its first pre-release, 0.2.0, was tagged on 12 Nov 2026. It hasn't run against a library's own tenant.
- **The desktop app:** phases D1 to D3 of [desktop-plan.md](desktop-plan.md) are built (PRs [#17](https://github.com/ByYudkowskysTentacle/FOLIO-Exchange/pull/17) to [#19](https://github.com/ByYudkowskysTentacle/FOLIO-Exchange/pull/19), 28 and 29 Oct 2026) and usable as a preview. D4, the tray icon and notifications, was built on 12 Nov 2026. D5, the installer, is next, and D7, updates, is planned in [updates-plan.md](updates-plan.md).
- **Custom recipes (13 Nov 2026):** the desktop app can build a recipe for a vendor that has published none, from nothing or from a copy of an installed recipe, and change one it built (Recipes > "Build a custom recipe…"). The rules live in `recipeops.py`, outside the app's widgets. It hasn't been tried on a real vendor's layout yet, and the browser page and the command line can't build one (next steps, item 3).
- **PySide6 on Python 3.10 and 3.11 (13 Nov 2026):** with the pinned PySide6 6.12.0, a Qt call that returns nothing or no object costs None a reference, a signal's emit or a disconnect that works costs True one, and a disconnect that finds nothing connected costs False one, on those two Pythons only. No other object loses any: about 800 cached ones were watched across some 90 Qt calls. A window left open long enough would have stopped with "deallocating None"; CI's Python 3.10 job met it first, as an abort at exit once the recipe builder's tests were added. The app now gives None, True and False spare references before Qt starts (`desktop.spare_constants`). It hasn't been reported to Qt yet (next steps, item 4).
- **Unattended upkeep (12 and 13 Nov 2026):** the site's log rotates at 5 MB when a program starts, failed scheduled runs are retried over about a day instead of three hours, a retry that fails the same way sends no second alert, a slot that runs out always gets its given-up alert, a login the vendor's SFTP server refuses isn't retried in the slot, and the alert payloads and email TLS rules are tested (improvement plan 4.1). The run history and cache carry a format number, so a version never uses a database a newer one wrote, a damaged history is said as such (and still alerts from the hourly task), and the tray's own files stay on the PC (`%LOCALAPPDATA%`) rather than in a roaming profile. A review by a second model on 12 Nov found ten bugs in the first version of this work, all fixed on 13 Nov with regression tests.
- **[cHQ FOLIO Exchange Recipe](https://github.com/ByYudkowskysTentacle/cHQ-FOLIO-Exchange-Recipe)** (called FOLIOHQ until 28 Oct 2026) is, since 27 Oct 2026, the home of the `chq-academic` recipe and the collectionHQ Academic setup guide (`docs/setup.md`) and file layout (`docs/layout.md`). Its `docs/HANDOFF.md` has the collectionHQ status and open questions.
- **Phase 0, `folio-chq-extract`**, the one-vendor tool this platform generalizes, moved to that repository's `legacy/` folder. It stays installable and tested as a fallback until FOLIO-Exchange makes its first real delivery. Its status:
  - Tested end to end against FOLIO's public reference systems (Okapi and Eureka).
  - The cHQ Academic file layout is implemented.
  - The cHQ SFTP login is verified.
  - It has **not** yet run against the library's own tenant, and nothing has been uploaded to cHQ.
- **The pilot library**, the first library setting up FOLIO-Exchange (not named in these docs), **is on Eureka.**

## v1 build (26 Oct 2026)

The contract is `docs/design.md`; it was revised after a three-lens design review (spec coverage, safety and correctness, operator UX and FOLIOHQ parity), and its last section lists what was reviewed and left for later.

**Done**
- The whole pipeline: recipe library and feed overlay, read-only FOLIO client with patron and redirect guards, sync, MARC and delimited builders, checks, SFTP and local delivery, run history and audit, schedules, alerts, the runner, the command line and the guided `init`.
- Safety from the review: first delivery held per destination and per recipe major version; `release` shows the run, checks file hashes and asks first; partial SFTP deliveries recorded; manual runs never cancel a scheduled delivery; full syncs refuse a truncated download; https and TLS for SMTP required; shared recipes cannot set where files go or which server key to trust; relative paths taken from the site folder; hand edits to settings audited.
- A design and function review on 27 Oct (`docs/review-2026-10-27.md`) verified 71 findings; the 27 in "Fix now" are fixed, and the rest are planned in `docs/improvement-plan.md`.
- Batch 1 of the plan is done: any change to a feed's delivered layout holds the next delivery and says what changed; `check`, `feeds` and the page warn when the hourly task has not run for two hours, and an optional heartbeat URL tells an outside monitor; `check` warns about folders other Windows users can change, and the guide installs under `%LOCALAPPDATA%`; `folio.ca_bundle` (a PEM file or the Windows certificate store) replaces turning TLS checks off; the page opens only through a one-time link; staff data is dropped from cached records; dependencies are pinned in `constraints.txt`. No release tag yet: the guide and installer still install `main`.
- Batch 2 of the plan is done: a shared feed-operations core (`feedops.py`), paused and dry-run feeds handled plainly on the command line, a schedule command that works in PowerShell, guide sections for going live and updating, and a keyboard-usable, self-refreshing page.
- A second review round on 27 Oct (`docs/review-2026-10-27-round-2.md`) verified 19 findings in the areas the first covered thinly: values in the files, unattended runs, living with the tool over time, and settings as a safety boundary. All 19 are fixed (PR [#12](https://github.com/ByYudkowskysTentacle/FOLIO-Exchange/pull/12)): legacy notes read strictly, a hold on the first delivery from another FOLIO, alerts for failing or given-up passes, a task that runs on battery, typed SFTP key pins, and a fuller settings audit among them.
- A final review found 14 bugs (each reproduced) and an operator walkthrough found 15 usability problems; all are fixed, with regression tests (`test_regressions.py`, `test_walkthrough.py`).
- `chq-academic` 1.0.0 writes byte-identical `.mrc` and `.psv` files to folio-chq-extract from the same data. Since 27 Oct 2026, the CI of cHQ FOLIO Exchange Recipe checks it on every change.
- At that point, 202 offline tests (`pytest`), `ruff` clean, JSON Schemas and commented examples. CI passes on Linux (Python 3.10 to 3.13) and Windows, with a gitleaks secret scan. Merged to `main` in PR [#1](https://github.com/ByYudkowskysTentacle/FOLIO-Exchange/pull/1).

**Eureka trial (26 Oct 2026).** Run against the public Eureka Snapshot reference system (`https://folio-etesting-snapshot-kong.ci.folio.org`, tenant `diku`, the published demo login), delivering to a local folder:
- `check`: login and every endpoint readable (10,042 instances, 27 holdings, 33 items, 15 loans, ten reference tables).
- `run chq`: a full sync in 30 seconds (10,000 MARC records fetched), held as a first delivery; `release` sent it; the next run was a delta of under 4 seconds and delivered straight away.
- A feed with `bibs_without_items: true` built 10,041 bibs (10,000 from SRS). Every record parsed; 001 = instance HRID and 999 ff $i = instance UUID on all of them; leader 9 = `a`; no duplicates; every PSV row had 20 columns and linked to a bib.
- `init` ran end to end with typed answers: login, permissions, the tenant's own locations, a live preview, a local delivery test.
- Fixed from what it showed: previews sampled the first instances by id, and on this tenant (like a library with many e-resources) none had items, so previews were empty. They now start from items. Also: the password note in `check` and `schedule` now matches where `site.yaml` says the password is; the wizard writes `secret: env:FOLIO_PASSWORD` when the password stays in the environment, and no empty `filters`; `check --delivery` names the local folder.
- In this sample data every instance with items is FOLIO-source, so the default chq feed sends generated bibs only; a real tenant will mostly send SRS MARC, as the all-bibs feed showed.

**Not done:** nothing has run against the library's own tenant or a vendor server; the Windows scheduled task, keyring use under it, and the Teams card are untested outside mocks. Since 27 Oct 2026, gate 1 goes through FOLIO-Exchange, with the legacy tool as the fallback.

**Next**
1. A dry run against the library's own tenant: `docs/dry-run.md` is the guide. The operator runs it; the password goes from their keyboard into Windows Credential Manager and is never shared.
2. Gate 1: the first delivery to collectionHQ, following the `docs/setup.md` of cHQ FOLIO Exchange Recipe (see Next steps below).
3. Try the hourly Windows task (`folio-exchange schedule`) on the library PC, with the password in Credential Manager.

| Date | Decision | Why |
| --- | --- | --- |
| 2026-10-26 | Eureka first; Okapi kept only while the same code covers it, with no Okapi-only work | FOLIO is moving to Eureka, and the first library is already on it |
| 2026-10-26 | New repo FOLIO-Exchange; FOLIOHQ stays as phase 0 | Keep the working cHQ tool stable while the platform is designed |
| 2026-10-26 | The operator is a systems librarian: v1 is a guided command line plus recipes; the web UI is phase 2 (superseded by the local page and the desktop app, below) | Matches who will actually run it |
| 2026-10-26 | It runs on each library's own PC or server, inside its network | FOLIO hosts usually accept API traffic only from known networks |
| 2026-10-26 | Outbound feeds after cHQ are unranked candidates | The second recipe is whichever a partner library needs first |
| 2026-10-26 | Writing into FOLIO (inbound loads) waits for v2, behind a separate account and a second approver | Writes carry far more risk than reads |
| 2026-10-26 | Working name FOLIO-Exchange | Check FOLIO's trademark guidance before announcing it |
| 2026-10-26 | MIT license, the same as FOLIOHQ | One license across both tools; FOLIOHQ's code is reused here |
| 2026-10-26 | Start a simple UI early, before gate 1: a local page served by `folio-exchange ui`, laid out like Postman, with no new dependencies | The dry run waits on the library's credentials. The page reuses the runner, so it adds no new path to FOLIO or a vendor |
| 2026-10-26 | A delivery to a new destination, or on a new recipe major version, waits for a person to release it | A test delivery to a local folder must not disarm the review of the first real upload |
| 2026-10-26 | Recipe minor and patch versions never change an output's bytes; any layout change is a new major | `^1.0` updates automatically, so a vendor must never see an unreviewed change |
| 2026-10-26 | A shared recipe sets only how files travel (transport, upload mode); hosts, folders and server keys are local | A recipe from another site must not choose where files go or which server to trust |
| 2026-10-27 | FOLIOHQ becomes the home of the `chq-academic` recipe and its documentation; its tool moves to `legacy/` as a fallback, and gate 1 runs on FOLIO-Exchange | One engine to maintain. The recipe and the collectionHQ docs live with what was learned about collectionHQ, and byte parity, checked in FOLIOHQ's CI, lets a library switch either way |
| 2026-10-27 | Legacy item notes are read strictly here (ISO 8601, `legacy.date_format`, or free text with a day, month and year; dates from 1800 to tomorrow; one whole number for counts), while FOLIOHQ's legacy tool still reads them leniently. FOLIOHQ's setup docs should state the accepted note formats, and add `host_key_type: ssh-rsa` to collectionHQ's pin | Lenient reading sent wrong dates and counts with no warning (second review round). The legacy tool is a fallback, not worth changing; byte parity runs without legacy settings, so it still holds. collectionHQ's server key is RSA, and a typed pin keeps deliveries working if the server adds a newer key type |
| 2026-10-28 | FOLIOHQ renamed cHQ FOLIO Exchange Recipe (`ByYudkowskysTentacle/cHQ-FOLIO-Exchange-Recipe`); the recipe source keeps the id `foliohq` | The name says what the repository now holds. GitHub redirects the old name, and installed sites keep their record of where their recipes came from |
| 2026-10-28 | Batch 3 (large catalogues) tabled; a desktop app planned in `docs/desktop-plan.md` | The pilot library's catalogue is about 70,000 records. A window of its own and a one-file installer remove the steps where staff get stuck |
| 2026-10-28 | The desktop app is a native PySide6 (Qt) app, built now, with a tray icon and notifications in the first build; a self-contained Windows installer first, with the pip route kept for IT staff; signed through SignPath Foundation, unsigned for the pilot until accepted; Windows only. The browser page is retired once the app matches it | One language with the core, no local web server to defend, mature screen reader support. A page in a native window, Rust, wxPython, Tkinter, Flet and C# were compared (`docs/desktop-plan.md`). SignPath is free for open source; Azure Artifact Signing, a paid service, is the fallback |
| 2026-11-03 | Naming: **site** stays the name of the local folder (one FOLIO tenant's connection, shared cache, run history and alerts; it holds feeds to many services). A **service** is a third-party platform the library sends data to (collectionHQ, OCLC, discovery layers). A **destination** is where a service receives the data: today an SFTP server, folder and account with a pinned server key, or a local folder; later, API endpoints. **Tenant** appears in app text only for the FOLIO tenant itself ("FOLIO tenant fs00001234"). Renaming site to service, or to tenant, was rejected. Making services and destinations objects of their own is planned in `docs/services-plan.md` | A site shares one FOLIO login and cache across services, so one folder per service would mean a full catalog sync per vendor. "Set up / Rename / Delete tenant" would read like FOLIO platform operations. Naming the far end now keeps "data from FOLIO, through feeds, to services" clear once vendors offer automatic setup (API keys, OAuth, provisioning links) |
| 2026-11-12 | The vendor's server key fingerprint is optional. Without it, setup pins the key the server shows (trust on first use, as OpenSSH's `accept-new`) with `host_key_confirmed: false`, and logins, runs and tests go ahead with it. A changed key is still refused, and saving a server whose pinned key has gone needs the vendor's fingerprint. The vendor's fingerprint confirms the pin later | A vendor may give a password and no fingerprint (collectionHQ's key in these notes was read from the server, not received from them), and an unconfirmed key paused the feed and refused every login, so nothing could be delivered. Pinning on first use keeps every later login checked; only the first read relies on the network path |
| 2026-11-12 | Failed scheduled runs are retried 1, 2, 4, then every 8 hours later, counted on the hourly starts, and `max_attempts_per_slot` defaults to 6 (about 23 hours). A slot is given up after the last attempt that fits before the next, and a slot that ran out while the PC was off is reported by the next pass. A retry that fails with the same error as the slot's attempt before it sends no alert, and a login the vendor's SFTP server refuses isn't retried in the slot | Three hourly attempts gave up a weekly delivery after an outage of three hours, such as a hosted FOLIO's weekend maintenance (the second review round's SCHED finding). Six alerts for one outage would be noise; the first failure and the given-up alert say it, so the given-up alert must never be lost. Six tries of a wrong password could lock a vendor account |
| 2026-11-12 | The tray watches only the sites a person turns it on for under Options (`tray.json` in the app's folder for this PC, `%LOCALAPPDATA%\FOLIO-Exchange\.app`), one tray per Windows user. Starting it at sign-in is a separate, opt-in value under this user's Run key. It notifies about scheduled runs only, plus the task stopping (once the tray has been awake long enough for the task's hourly start) and feeds going overdue | A demo or test site must not produce notifications. Runs started by hand are seen where they were started. A per-user Run value needs no administrator rights and is easy to remove |
| 2026-11-12 | In-app updates planned in `docs/updates-plan.md`: a notice first (U0), downloads checked against the project's own signature over `SHA256SUMS` once the installer exists (U1), installs in place once releases are signed for Windows (U2). Never without a yes, never during a run, and going back never puts settings back wholesale | A key held off GitHub, not GitHub or SignPath's shared publisher name, proves a release came from this project; a wholesale restore could start delivering a feed someone paused after the update |
| 2026-11-12 | Version 0.2.0, tagged `v0.2.0` and published as a GitHub pre-release. The guide and the installer still install `main` by default; the tag installs on request | A fixed version for the pilot library's PC and for bug reports before gate 1. Installing a tag by default waits for gate 1, as `docs/design.md` says |
| 2026-11-13 | A library builds custom recipes in the desktop app, for everything the recipe format allows. A custom recipe is one file at version 1.0.0 in the site's recipes folder, **changed in place**: feeds follow from their next run, and the layout hold reviews any change the vendor would see. The core works out `reads` from the fields used and always writes `patron_data: none`. Only recipes built on the site are changed; others are copied under a new id that no vendor source provides. The browser page and the command line get the builder later (next steps) | Editing in place, rather than a new version per change, was the maintainer's choice. What makes it safe is that the hold already compares what was last delivered with what would be sent, however the recipe came to change. "A published version never changes" still holds for every recipe that is shared; a custom recipe never leaves the site unless someone publishes it, and then it follows the versioning rule. Reads worked out by the core keep a hand-built recipe from asking FOLIO for more than its columns need |
| 2026-11-13 | On Python 3.10 and 3.11 the desktop app gives None, True and False 2^40 spare references each before the first Qt call, by adding to the count in the object's first field after checking that field against `sys.getrefcount`. Python 3.12 and later are left alone | PySide6 6.12.0 loses one reference to None or True per Qt call on those Pythons (measured with PySide6 alone: 3.10.22 and 3.11.18 lose them, 3.12.16 doesn't). The other ways out were to stop supporting Python 3.10 and 3.11 for the app, which the installer accepts today, or to move the pinned Qt, which nothing shows would help. Both stay open to the maintainer; this keeps what is supported working meanwhile |

Still open: patron data, upkeep and funding, a proposal to the FOLIO community (its Reporting SIG, a special interest group), and the name check.

## Lessons carried over from folio-chq-extract

**Vendor specs**
- cHQ Academic links items to bibs on **Bib record ID = FOLIO instance UUID = MARC 999 ff $i**, which SRS writes. It does not use 001 or a barcode. folio-chq-extract enforces 999 ff $i on every record (`MarcBuilder.finalize`).
- cHQ's PSV layout has 20 columns, pipe-delimited, with `None` for empty values and its own header names. The `chq-academic` recipe and the legacy tool's `legacy/config.example.yaml` reproduce it exactly.
- Vendor sample files get mangled in transit. cHQ's sample `.marc` had its field and subfield separators (0x1E, 0x1F) turned into newlines and ` $`, so no MARC reader could open it. Validate binary MARC on intake, and ask vendors for the original file, zipped.

**collectionHQ SFTP (US)**
- **Host:** `sftp.us.collectionhq.com:22`, an AWS Transfer Family server.
- **Host key:** RSA `SHA256:qt5HxgZ6ktlwhFUUAwdjMZlL2KkAbKXhy2TsRxWoITI`. This was read from the server on 26 Oct 2026, not received from cHQ, so confirm it with them.
- **FTP host:** `ftp.collectionhq.com` is plain FTP only, so it is unusable.
- **Account:** the library's service account was described as upload-only, so folio-chq-extract uses `upload_mode: direct`, with no stat and no rename. Listing the login folder works.
- **Folders:** the login folder contains `holds/` and `transactions/`, which look like other cHQ feeds. Which folder bibs and items go into is still to confirm with cHQ.

**FOLIO**
- `POST /authn/login-with-expiry` works on both Okapi and Eureka (through the Kong gateway).
- **Public reference systems:** current URLs and demo logins are listed at https://folio-org.atlassian.net/wiki/x/9oCeHg. As of Oct 2026, the Eureka API is `https://folio-etesting-snapshot-kong.ci.folio.org`, tenant `diku`, and the environment is rebuilt daily, so record counts change. These are public demo accounts, not secrets.
- **What FOLIO already does natively** (checked in docs.folio.org, Oct 2026):
  - Data Export builds MARC (including holdings and item fields), but its docs describe no schedule or delivery.
  - EDI order exports to vendors are scheduled, over FTP or SFTP.
  - Bursar transfers are scheduled (Settings > Users > Transfer criteria).
  - OAI-PMH serves `marc21_withholdings` to systems that harvest.
- Keyset paging (`id>"last" sortBy id`) is required for large collections; offset paging degrades badly.
- Never read or export patron data. Loans keep `itemId` and dates after anonymization, which is all circulation counts need.

**Secrets and accounts**
- Passwords come from environment variables or the OS keyring (`keyring` package; Windows Credential Manager on Windows). folio-chq-extract uses the services `folio-chq-folio` and `folio-chq-sftp`, keyed by username.
- Tests must never touch a developer's real credential store. folio-chq-extract's tests block the real keyring with an autouse fixture.
- Nobody working on the project, AI assistants included, signs in to a library's production FOLIO tenant or vendor server with that library's password. They hand the library's operator a command to run, and never read, print or write the password.
- A credentials text file nearly got committed to a public repo. Ignore credential-looking files by default (see `.gitignore`).

**GitHub**
- Current Node 24 action versions (Oct 2026): `actions/checkout@v7`, `actions/setup-python@v7`, `actions/cache@v6`, `actions/upload-artifact@v7`. CI pins each action to the full commit SHA of its tag, with the tag in a comment; look the commit up read-only with `gh api repos/<owner>/<repo>/commits/<tag> --jq .sha` when moving to a new version.
- Commits use the GitHub noreply address, so no personal email is published.

**Refreshing `constraints.txt`** (on purpose, in a change of its own; CI and the installer both install with it):
1. In a fresh venv on Windows with Python 3.12, install FOLIO-Exchange alone, so pip picks the newest versions: `py -3.12 -m venv ../venv-constraints` (outside the repository), then `../venv-constraints/Scripts/python -m pip install .`
2. `../venv-constraints/Scripts/python -m pip freeze --exclude folio-exchange` lists the runtime packages. Put those lines in `constraints.txt` under its header. Keep the environment markers: `sys_platform == "win32"` on `pywin32-ctypes`, and the `python_version` pairs for packages whose newest version needs Python 3.11 (check on PyPI which version is the newest for 3.10). Leave out the Linux-only and older-Python packages the header names.
3. Install the dev tools with the new file (`../venv-constraints/Scripts/python -m pip install -c constraints.txt -e ".[dev]"`), run the tests and ruff, and let CI check Linux (Python 3.10 to 3.13) before merging.

## Next steps

1. **Gate 1 with FOLIO-Exchange**, following the `docs/setup.md` of cHQ FOLIO Exchange Recipe:
   - **Connect:** get the library's FOLIO API (Kong) URL, the tenant ID and a read-only service account, then run `folio-exchange init`, `check` and `run chq --no-deliver`.
   - **Analyze:** review locations, call numbers and counts in that output.
   - **Agree with cHQ:** the remote folder and host key, plus a sample for their approval.
   - **First delivery:** `run chq`, then `release chq`. cHQ accepting it is gate 1. If FOLIO-Exchange is blocked, the legacy tool sends the same files.
2. **Services and destinations** (`docs/services-plan.md`): after the desktop app's D4 (tray and notifications), make services and destinations objects of their own. Phases S1 to S4 come before a second service, and S5 (service definitions from vendors) before the first automatic integration. Its open questions, and its suggested text for the spec's terms and roadmap, wait on the maintainer.
3. **The recipe builder, after its first version** (13 Nov 2026; the desktop app only). Each step calls `recipeops.py`, which already holds the rules, so it adds an interface and no rules of its own:
   - **Parity, the page:** `GET /api/recipes/builder?copy=ID|edit=ID` (`recipeops.builder_form`), `POST /api/recipes/review` (`recipeops.review`) and `POST /api/recipes/custom` (`recipeops.save_custom` with `via="ui"`, as a job, carrying the file's version), then the form in `web/app.js` with the app's four tabs, its checks before the core is asked, and the same words. Add "Copy to a custom recipe…" and "Edit recipe…" to the page's Recipes view, and port `tests/test_desktop_builder.py`'s cases to `test_ui.py`. The desktop plan gives the page fixes only until D8 decides whether it stays, so this waits on that decision.
   - **Parity, the command line:** `recipes new [--from ID]` writing a commented draft file for an editor, `recipes check-draft FILE` (`review`) and `recipes save FILE [--replace]` (`save_custom` with `via="cli"`), so a custom recipe can be made on a server with no desktop.
   - **Read a vendor's sample file** (asked for with the first version, left for later): choose the vendor's sample delimited file, read its separator and header row, and match each header to a field, starting from names that are alike. Keep the file as `samples/<output name>.<ext>` so the conformance check (VAL-2) uses it.
   - **Preview a draft** with a sample of live records before it is saved (today: save it, add a feed, which starts as a paused dry run, and use Preview).
   - **Delete a custom recipe** that no feed uses, and **export** one as a folder ready for a pull request to a vendor's recipe repository, where it becomes a published recipe under the versioning rule.
   - **The spec:** MAP-2 and the roles table say a visual editor and a field picker arrive with the phase 2 web UI. Suggested text for the live spec, for the maintainer: "In v1 the desktop app builds custom recipes with a field picker; screens for more staff follow in phase 2."
4. **PySide6's lost references on Python 3.10 and 3.11** (13 Nov 2026): report it to Qt for Python with the two-line loop that shows it (`QWidget.setVisible` and `Signal().emit()`, watching `sys.getrefcount`), and check each new PySide6 before moving the pin. PYSIDE-2660 was the same failure in an earlier version, fixed in 6.5.6, 6.7.1 and 6.8.0. The 6.12.0 wheel's own reference counting looks like Python 3.12's, which leaves these three objects uncounted because 3.12 never frees them. Decide whether the app should need Python 3.12 or later instead: the installer already installs 3.12 when it finds no Python. When PySide6 no longer loses them, take `desktop.spare_constants` out.
